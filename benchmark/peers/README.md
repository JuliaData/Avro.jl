# Avro.jl against other Avro libraries

This directory measures Avro.jl against fastavro, Apache Avro Java, apache-avro (Rust), arrow-avro (Rust) and
hamba/avro (Go) on the same files, with every reader checked against the others. The analysis is written by hand;
the tables between the markers at the end are generated by `run.jl`.

## Verdict

Avro.jl is the fastest reader here of fixed-width data with every codec and of event-log data with every codec
but zstandard, where it is level, and the fastest deflate reader and writer of every shape but nested reads. It
trails on string-heavy rows, on nested data, and on uncompressed writes of strings and records. Figures are medians of 3 runs per side, single-threaded unless marked;
a ratio is how many times faster Avro.jl is, so below 1 means slower.

**Where Avro.jl leads.**

- Fixed-width numbers: typed rows (`Avro.Rows(path, T)`) read 10M rows in 0.530 s with the null codec, 1.96× the
  fastest peer (arrow-avro, 1.04 s) and 2.37× Java's fastest. With deflate, zstandard and snappy they are 1.50×,
  1.66× and 2.45× the fastest peer. A typed table (`Avro.Table(path, T)`) is 1.14× to 4.53× arrow-avro, its
  columnar counterpart.
- The event log: typed rows are 1.10× arrow-avro with the null codec, 1.55× with deflate and 1.36× Java with
  snappy, and level with arrow-avro with zstandard (1.07 against 1.10 s, overlapping ranges).
- Deflate, which Avro.jl runs on libdeflate: reads of the numeric, strings and event-log files are 1.17× to 1.55×
  arrow-avro and 1.71× to 2.65× Java, and writes of every file are 1.43× to 1.91× the fastest peer.
- With 14 threads, `Avro.Table(path; ntasks)` reads the numeric, strings and event-log files in 0.15 to 0.57 s
  with every codec, faster than any single-threaded reader, and nested data faster with deflate and snappy. Deflate
  writes compress blocks on every thread: 0.55 to 1.30 s, against 3.4 to 8.1 s for the fastest single-threaded
  peer.
- Uncompressed numeric writes are level with arrow-avro (0.448 against 0.440 s) and 1.37× Java.

**Where Avro.jl trails.**

- Strings: typed rows are 0.72× Java's custom coders with the null codec (0.866 against 0.623 s) and 0.74× with
  snappy, and 0.91× arrow-avro with zstandard. Uncompressed string writes take 0.844 s, 0.40× hamba and 0.53×
  arrow-avro.
- Nested data: arrow-avro reads it 1.3× to 2.1× faster than typed rows with the null, deflate and zstandard codecs;
  typed rows are level with or faster than Java (0.99× to 1.57×). A one-thread generic table is 0.22× to 0.53×
  arrow-avro.
- Uncompressed writes of the event log and nested data are 0.64× and 0.65× arrow-avro.
- Generic `Avro.Record` rows are 0.64× to 0.94× Java's GenericRecord with the null, zstandard and snappy codecs,
  and 1.24× to 1.59× with deflate.
- A typed table with `String` fields reads the strings file in 2.35 s, twice a generic table's 1.13 s.

A claim the numbers support: "the fastest reader of fixed-width and event-log data, the fastest deflate reader and
writer, and the fastest multi-threaded table reader", with the exceptions above. The remaining gaps and their
causes are below.

## Rerun

```sh
cd benchmark/peers
julia run.jl                                   # full matrix: 5 runs per side, about 3.5 h on a quiet machine
julia run.jl --quick                           # 2 runs per side, mixed + strings, null + deflate
julia run.jl --avro /path/to/Avro.jl           # against another checkout (default: this one)
julia run.jl --report results/<run>.tsv        # rebuild the tables from a finished run
```

`run.jl` needs Julia, a Rust toolchain, Maven with a JDK, Go and Python 3 on the `PATH`. It builds every side
(cargo, Maven, go, a Python venv with fastavro, and a Julia environment that `Pkg.develop`s `--avro`), generates any
missing data, runs the sides in rotating order, and writes `results/<run>.tsv`, `results/<run>-tables.md` and the
tables below. `--shapes`, `--codecs`, `--sides`, `--ops`, `--runs` and `--maxload` narrow a run. The data in
`data/` totals about 6 GB and takes about 15 minutes to generate; `data/out/` holds the last written files (about
13 GB) and can be deleted.

Start one run at a time: each run's setup re-points `julia/Manifest.toml`, and every row starts a fresh process
that reads the bench sources, so editing them or the Avro.jl checkout during a run mixes versions. The driver
waits up to 10 minutes whenever the 1-minute load average exceeds `--maxload` (default 20) and then runs anyway,
recording the load before every run. Re-measure whole cells, not single rows, so the rotation stays fair. When its
output is redirected, the driver's stdout is block-buffered; the TSV is flushed after every row.

`profile/` holds the scripts behind the analysis: `avrojl.jl` (the Julia profiler, by self and inclusive
samples), `sample.sh` (macOS `sample` for native code), `gcscan.jl`, `utf8check.jl` and `codecs.jl`.

## What was measured

**Data.** `gen.py` writes each file once with fastavro from a fixed seed, flushing blocks at 64,000 bytes, the
Java implementation's default sync interval. Every codec of a shape holds the same rows.

| shape | schema | read rows | null file | write rows |
|---|---|---|---|---|
| numeric | 4 `long`, 2 `double`, `int`, `boolean` | 10,000,000 | 422 MB | 4,000,000 |
| strings | 10 `string`, 5 to 40 ASCII bytes each | 2,000,000 | 470 MB | 1,000,000 |
| mixed | event log: `long` id, `timestamp-micros`, `string`, `["null","string"]` (30% null), `double`, `int`, 5-symbol `enum`, `["null","long"]` (50% null), `boolean`, 16-byte `bytes` | 4,000,000 | 268 MB | 2,000,000 |
| nested | `long`, `array<long>` (0 to 10 items), `map<string,long>` (0 to 5 entries), record of (`string`, `double`) | 3,000,000 | 202 MB | 2,000,000 |

Reads cover the `null`, `deflate`, `zstandard` and `snappy` codecs; every implementation supports all four.
Writes cover `null` and `deflate`, at deflate level 6 for every writer, which is each library's default. Files are
read from the page cache, so these are warm-cache numbers bound by CPU.

**Checksum.** Every reader computes three sums over every decoded value. The first is the sum modulo 2^61 of every
`int`, `long`, `timestamp-micros` tick, enum ordinal, `true` boolean and IEEE-754 bit pattern of a `double`. The
second counts non-null strings, map keys and `bytes` values, and the third adds up their byte lengths. Every run of
every reader must report the same row count and checksum. Another implementation reads every written file back
(apache-avro, or fastavro for apache-avro's own files) and must get its input's checksum. The checksum runs inside
the timed region, so no reader can skip the work. It costs 22 to 31% of a fastavro read and little elsewhere.

**Timing.** Each run is a fresh process under `/usr/bin/time -l`, which reports peak RSS and user and system time.
The tables' "first" column is iteration 1, which includes Julia compilation and JIT warm-up in Java. The warm time
is the median of the process's last three iterations. Java runs 8 iterations for reads and 5 for writes; the other
sides run 2 to 4. The order of the sides rotates every round. A write side first reads the input file into its own
in-memory rows, untimed, and then times only the write. Single-threaded sides decode on one thread
(`julia -t 1`); the JVM's JIT and GC threads and Go's GC threads are not restricted, as in production. Rows marked
MULTI-THREADED use `julia -t auto`: 14 threads on 10 performance and 4 efficiency cores.

**Machine.** Apple M3 Max, 14 cores, 96 GB, macOS (Darwin 27.0). The machine was shared: another session's builds
and tests kept the 1-minute load average between 20 and 65 through the run in the tables, which inflates every
time but leaves the ratios between sides fair, since the sides alternate in rotating order. The multi-threaded rows
are the most sensitive to it. That run measured 3 rounds per side and left out fastavro, hamba/avro reads and
apache-avro, none of which was the fastest reader of any file in a first run of the full matrix (5 rounds per side,
against an earlier Avro.jl, at a load of 5 to 25: `results/20261105-093645-tables.md`). There fastavro took 5.0 to
23 s per read, apache-avro 1.7 to 4.9 s and hamba/avro 0.54 to 5.9 s, against 0.46 to 2.3 s for the fastest peer.

**Memory.** Peak RSS includes each runtime's baseline, measured on a 1,000-row file: Julia with Avro.jl 430 MB,
the JVM 89 MB, CPython with fastavro 25 MB, Rust and Go 6 to 7 MB. The JVM grows its heap to about 1 GB under
default flags. Avro.jl memory-maps files by default, so its peak RSS also counts the mapped file's pages: the typed
numeric read peaks at 772 MB with the map and 395 MB with `mmap=false`, at the same speed (0.38 against 0.40 s).
`Avro.Table` holds the whole table, while the arrow-avro side drops each batch after checksumming it, so the two
columnar RSS figures measure different things.

median run it was 0.62 s slower than the warm time for typed rows, which compile a decoder for their row type,
0.80 s for typed tables, 0.45 s for generic tables and 0.57 s for Java's JIT warm-up.

## Where Avro.jl trails, and why

Each limiter comes from a profile taken in a run that is not reported (`profile/avrojl.jl`, the Julia profiler at
0.5 ms, by self and inclusive samples), confirmed in the source.

1. **Nested data is bound by allocation.** Every array, map and nested record is its own heap object. Typed rows
   allocate 646 bytes per nested row, a `Vector{Int64}`, a `Dict{String,Int64}` and its key strings, and spend
   much of their time building each `Dict`. A one-thread `Avro.Table` keeps every such object alive, so 58% of its
   samples are inside garbage collection (4.2 s and 2.1 GiB per read). arrow-avro appends list items and map
   entries to shared buffers instead. The fix this points to is columns for arrays and maps like Avro.jl's string
   columns: one byte or value buffer plus offsets, with Julia values built on access.
2. **Typed string rows allocate a `String` per value.** Copying each string's bytes is 25% of a typed strings
   read, allocating and collecting the strings about 15%, and the ASCII check, which is the first read of each
   string's bytes and so waits on memory, about 30%. Java's custom coders copy each string into a `Utf8` the
   reader reuses and do not validate. A one-thread `Avro.Table` stores strings in shared buffers, but still spends
   its time on the same copy and check plus per-cell bookkeeping, and reads at 0.63× arrow-avro.
3. **A typed table's `String` fields are heap objects.** `Avro.Table(path, T)` holds a `Vector{String}` per
   `String` field, so the collector traces every value: on the strings file it reads in 2.35 s with 54% GC,
   against 1.13 s for a generic table. Typed tables would need the generic table's string columns for their
   `String` fields.
4. **Generic `Avro.Record` rows box every field.** Values live in a `Vector{Any}`, so a numeric read allocates
   3.05 GiB, about 330 bytes per row. Java's generic records box too, but bump-pointer allocation and a copying
   young collector keep its GC under 1%.
5. **A one-thread generic table pays a dispatch per cell.** On the numeric file a generic table reads in 1.31 s
   and a typed table, compiled for its row type, in 0.75 s. The difference is the closed chain of column builders
   that lets `Avro.Table` read any schema without compiling code for it.
6. **Uncompressed writes of strings check every string where it lies.** A Julia `String` may hold invalid bytes,
   so the writer checks each one before copying it into the block. In a profiled string write that check is about
   half the samples, but it is the first code to read each string, so most of its time is waiting for memory: a
   check 22% faster per string left the write's time unchanged.

## What limits the peers

- **fastavro.** The CPython interpreter and per-record dict building lead the macOS `sample`
  (`_PyEval_EvalFrameDefault`, `insertdict`, `_PyUnicode_Equal`); the Cython decoder itself is a minority. Its
  default `datetime` conversion is 17% of a mixed read.
- **Apache Avro Java.** JIT-compiled decoding with GC under 1% (`GarbageCollectorMXBean`). With custom coders,
  strings are byte copies into reused `Utf8` buffers (JFR). The class generated for the mixed schema, which has
  logical types, lacks custom coders (`hasCustomCoders()`), and with them enabled the mixed read is slower than with
  the fast reader (1.32 against 0.68 s).
- **apache-avro.** Allocation. malloc and free take about 40% of a numeric read, because each `Value::Record` is
  a `Vec` of (`String` field name, `Value`) pairs built per row.
- **arrow-avro.** Varint decoding (`Decoder::decode` plus `read_vlq`, two thirds of a numeric read) and copying
  string bytes into its buffer (`memmove`, 58% of a strings read). Its snappy reads are 2 to 3× slower than its
  null-codec reads, which was not profiled.
- **hamba/avro.** String copies and its struct codec (`readBytes`, `structDecoder.Decode`); Go's concurrent GC runs
  on other cores. Go 1.27's `compress/flate` at level 6 compresses the strings data to 96% of its size, where zlib
  and libdeflate at level 6 reach 76%, so hamba's deflate writes are fast because they compress less. The summary
  leaves out any compressed write more than 3% larger than the median for its cell.

## Notes

- Every reader agreed on every file's row count and checksum, and every written file read back identically through
  another implementation (the Checksums section of the tables).
- hamba/avro's `Decode` into a reused struct merges a map field's entries into the old map while it replaces
  slices, as `encoding/json` does, so the Go side zeroes the target before each row.
- Avro 1.12's class-security check rejects generated SpecificRecord classes unless their package is trusted
  (`-Dorg.apache.avro.SERIALIZABLE_PACKAGES=peerbench`).
